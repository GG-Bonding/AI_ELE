# V3 — Executable Skill Runtime & Policy Learning

V2 landed Experience Intelligence (attribution, conflict, Patterns, evolution, V2 SDK).
V3 does **not** further thicken Memory — it completes the evolution chain into safe execution:

```text
Experience → Pattern → Skill Candidate
    → Validate → Shadow → Activate
    → Skill Retrieval → Safe Execution
    → Outcome → Feedback → Skill Utility → Evolution
```

## Positioning

| Version | Answers |
| --- | --- |
| V1 | What experiences did I learn? |
| V2 | Which are trustworthy, conflicting, abstractable? |
| V3 | Can stable knowledge become **safe, executable capability** that keeps learning? |

## V2 Contract Freeze

V3 **must not** change the semantics of:

| Surface | Contract |
| --- | --- |
| V1 Episode / Attempt / Outcome | Unchanged |
| Experience store / utility / Beta learning | Unchanged |
| Pattern retrieve / generalize / evolve | Unchanged |
| Feedback targeting / attribution | Unchanged |
| Context provenance (`context_id`) | Unchanged |
| V2 SDK Episode / Action / Pattern APIs | Additive only |
| Learned PATH Recovery Benchmark | Results must be identical with `skill_runtime.enabled` on or off |

V2 `SkillCandidate` remains an **advisory description** (`auto_execute: false`). Execution is gated behind `skill_runtime`.

## Feature gate

```yaml
skill_runtime:
  enabled: false   # default — V3 execution paths stay dark
```

Env override: `AEE_SKILL_RUNTIME_ENABLED=1|true`.

When `enabled: false`:

- No Shadow / Live Skill execution
- No Skill retrieval into context
- ProposeSkill / GetSkill (V2 candidates) continue to work

## Non-goals (V3 phase 1)

```text
❌ Arbitrary code / shell / Python / eval
❌ Unrestricted HTTP or SQL tools
❌ Dynamic code download
❌ Auto-generated Tool deployment
❌ Multi-agent Skill orchestration
❌ Skill marketplace / cross-tenant sharing
❌ Foundation-model fine-tuning / PPO
❌ Auto-execute CRITICAL risk operations
```

**Skill V1 = declarative workflow DSL that may only call registered Tools.**

## Architecture (target)

```text
Pattern → Skill Candidate → Compiler/Validator → SkillVersion
    → Shadow Runtime → ACTIVE
    → Retriever → Selector → Policy Gate → Runtime → Tools
    → Outcome → SkillLearningEvent → Utility → Evolution
```

Parallel research track (later): counterfactual offline replay → Skill selection policy (bandit / ranking — not LLM weights).

## Definition of Done (V3 overall)

1. Pattern can produce a legal `SkillVersion`
2. Skills pass static validation before any run
3. Shadow run executes end-to-end without side effects
4. Missing tool / permission / risk blocks execution
5. ACTIVE skills can participate in tasks
6. Success/failure updates Skill utility (exactly-once)
7. Bad skills auto-suspend
8. Skill-enabled benchmark beats Pattern-only **and** `UnsafeActionRate ≤ baseline`

## V3-1 SkillSpec + SkillVersion (landed)

Logical `Skill` + immutable `SkillVersion` with declarative Spec IR:

```text
YAML  →  ParseYAML  →  Normalize(Spec)  →  SpecHash
                              ↓
                     SkillVersion (CANDIDATE / PENDING)
```

Spec may only declare registered tools in `steps[].tool` (enforced in V3-2). Runtime never interprets YAML directly.

Tables: `skills`, `skill_versions` (migration `000024`). V2 `skill_candidates` unchanged.

## V3-2 Validator + Tool Registry (landed)

`internal/toolregistry` — Tool Contract (input/output schema, Risk, SideEffect, tenant allowlist). Default catalog: `jira.search_projects` (READ_ONLY), `jira.create_issue` (LOW), `jira.delete_issue` (HIGH).

`internal/skillvalidator` — static checks before any Shadow/Live run:

| Check | Examples |
| --- | --- |
| Schema | duplicate step id / save_as, max_steps hard cap |
| Tool | registered, required args, unknown args (warn) |
| Refs | `{{ inputs.* }}` / prior `save_as.*` only (no forward refs) |
| Security | forbidden tools (shell/python/…), tenant allow, risk understatement, CRITICAL deny |

`ApplyToVersion` / `ApplyValidationReport` → `VALIDATION=PASSED` + `Status=VALIDATED` on success.
