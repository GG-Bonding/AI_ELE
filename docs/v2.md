# V2 — Experience Intelligence

V1 solved runtime experience learning:

```text
Experience can be produced → used → feedback received → utility changed
```

V2 solves harder questions:

```text
Which experience caused success/failure?
What if experiences conflict?
Can duplicates merge?
Can concrete experiences become Patterns/Skills?
```

## Positioning

| Version | Focus |
| --- | --- |
| V1 | Runtime Experience Learning |
| V2 | Experience Intelligence & Evolution |
| V3 | Executable Skill Runtime & Policy Learning — [docs/v3.md](v3.md) |

V2 pillars:

```text
Attribution + Conflict + Generalization + Evolution
```

### V2.2-7 Learned PATH recovery benchmark (landed)

Unlike V2-10 (seeded store + pre-run conflict resolve), this benchmark starts from an **empty store** and learns through the full Trace→Experience→Conflict path:

```text
cold_start (Env V2 strict, no recovery)  → fail baseline
train_v1 / probe_v1 (Env V1 lenient)     → learn E1 (display-name tip)
shock_v2 (Env V2 strict + recovery)      → negative transfer under stale E1
recover_v2                               → extract E2 → CONFLICT → SUPERSEDES
probe_v2                                 → E2 ACTIVE, E1 DEPRECATED
```

Metrics: **FGT** (probe_v1 − cold), **FWT** (late − early train), **NegativeTransfer** (shock failures), **RecoveryTime** (episodes from first V2 shock until clean probe_v2).

```bash
go test ./internal/eval/ -run TestLearnedPATHRecoveryAfterEnvShift -v
```

### V2.2-4 Structured semantic Judge (landed)

Hybrid judge (default when LLM is enabled on the server):

```text
similarity < 0.82          → UNRELATED (skip LLM)
opposing polarity          → CONFLICTS / POLARITY (skip LLM)
sim ≥ 0.98 + high overlap  → SAME (skip LLM)
mid-band / structured      → LLM StructuredJudgment
LLM failure                → HeuristicDedupJudge fallback
```

Structured relations map onto store decisions:

| Relation | Store DedupDecision |
| --- | --- |
| SAME | SAME (reinforce) |
| SUPPORTS / SPECIALIZES / GENERALIZES | RELATED (insert both) |
| CONFLICTS / SUPERSEDES | CONFLICT (insert + resolve) |
| UNRELATED | DIFFERENT |

VIP specialization (45d vs 30d) → `SPECIALIZES` → RELATED, not SAME/CONFLICT. Temporal policy update (30d → 14d) → `SUPERSEDES` → CONFLICT path.

## V2-4 Semantic Dedup (landed)

Two-stage store path:

1. **Exact** — within-episode `fingerprint` / `dedup_key` (unchanged)
2. **Semantic** — after embed, search same tenant/type/scope/(scope_key) neighbors; if cosine > 0.92, `DedupJudge` → `SAME` / `RELATED` / `DIFFERENT` / `CONFLICT`

| Decision | Store behavior |
| --- | --- |
| `SAME` | **Reinforce** existing row: merge `support_episode_ids`, raise **Confidence**; **do not** INSERT; **do not** change Utility |
| `RELATED` / `DIFFERENT` | INSERT new experience |
| `CONFLICT` | Do not merge (full conflict engine is V2-5); INSERT if no SAME neighbor |

Default judge: deterministic `HeuristicDedupJudge` (polarity + lexical overlap + auto-same ≈ 0.97). When LLM is enabled, `HybridDedupJudge` handles mid-band structured cases (V2.2-4).

API: complete-outcome / learning responses may include `reinforced_experiences` alongside `stored_experiences`.


## V2-5 Conflict Detection (landed)

When store-time semantic neighbors judge `CONFLICT`:

1. Still **INSERT** the new experience (do not merge)
2. Persist `ExperienceRelation{type=CONFLICTS}` between the pair
3. Close authority gap → both `ACTIVE` + `CONFLICTS`; clear gap → winner `SUPERSEDES` loser (V2-6)
4. Context selection **fail-closes**: either side with an unresolved CONFLICTS edge is `BLOCK`ed from auto-injection

```text
Candidate → Semantic neighbors → DedupJudge=CONFLICT
→ INSERT new row
→ Record CONFLICTS relation
→ Selector BLOCK (do not auto-use either side)
```

Default detector reuses V2-4 polarity heuristics (`HeuristicDedupJudge`). Postgres table: `experience_relations` (migration `000013`).


## V2-6 Supersession (landed)

When store-time polarity conflict is detected, compare **Authority** scores:

```text
Authority ≈ Evidence + SuccessRatio + Confidence + Utility + Freshness
```

| Gap | Action |
| --- | --- |
| `≥ 0.12` | Winner **SUPERSEDES** loser → loser `DEPRECATED`, `ExperienceRelation{SUPERSEDES}` |
| `< 0.12` | Keep both `ACTIVE` + unresolved `CONFLICTS` (selector still BLOCK) |

Deprecated losers drop out of default retrieval. Conflict peers involving non-retrievable experiences are ignored so winners are not blocked.

## V2-7 Generalization → Pattern (landed)

Concrete experiences can become a **Pattern** when a cluster passes gates:

| Gate | Default |
| --- | --- |
| Experiences | ≥ 3 retrievable, same `type` / `scope` / `scope_key` |
| Distinct episodes | ≥ 3 (`source_episode_id` + evidence support ids) |
| Avg utility | ≥ 0.70 |
| Conflict rate | < 0.10 (unresolved `CONFLICTS` pairs within the cluster) |

On success:

```text
Pattern (CANDIDATE) + pattern_evidence rows
+ ExperienceRelation{DERIVED_FROM}: pattern_id → experience_id
```

Default generalizer is heuristic (shared tokens + shortest content prototype). When LLM is enabled, `LLMPatternGeneralizer` produces evidence-grounded drafts (V2.2-5). HTTP: `POST /api/v1/patterns/generalize`, `GET /api/v1/patterns/{id}`, `GET /api/v1/patterns/{id}/evidence`. Postgres: `patterns` + `pattern_evidence` (migration `000014`).

## V2-8 Pattern Learning (landed)

Patterns are learnable artifacts, not frozen rules. They carry Beta utility (`alpha` / `beta`) like experiences.

```text
Supporting experience used → Feedback → Experience utility update
                                      → Pattern utility update (same signed reward)
```

| Behavior | Rule |
| --- | --- |
| Propagation | After a learning event applies to an experience, update every retrievable Pattern that lists it in `pattern_evidence` |
| Idempotency | Replay / already-applied events do not double-update Patterns |
| Promotion | `CANDIDATE` → `ACTIVE` when utility ≥ 0.75 and success_count ≥ 2 |
| Direct API | `POST /api/v1/patterns/{id}/reward` |

Migration `000015` adds `alpha` / `beta` / success / failure counts.

## V2-9 Skill Candidate (landed)

A proven Pattern can become a **Skill Candidate** — an executable-*looking* YAML blueprint for agents.

| Rule | Detail |
| --- | --- |
| Gates | Pattern `ACTIVE`, or strong `CANDIDATE` (utility ≥ 0.75, support ≥ 3) |
| Output | `skill_candidates` row + YAML with `auto_execute: false` |
| Idempotent | One skill per pattern |
| No execution | Engine never runs the skill (V3 territory) |

HTTP: `POST /api/v1/patterns/{id}/skill`, `GET /api/v1/skills/{id}`, `GET /api/v1/patterns/{id}/skill`. Migration `000016`.

## V2-10 Sequential Benchmark (landed)

PATH-inspired schedule comparing **V1 utility-only** vs **V2 intelligence** (conflict + authority supersession):

```text
probe_1 → train_positive → probe_2 → train_negative → probe_3
```

Seed: high-utility harmful tip + lower-utility but higher-authority helpful tip (same freshness / embedding).

| Arm | Behavior |
| --- | --- |
| `v1_utility` | Utility ranking prefers harmful → negative transfer |
| `v2_intelligence` | `ResolveConflict` SUPERSEDES harmful → helpful-only context |

DoD checks (enforced by test):

$$
SuccessRate_{V2} > SuccessRate_{V1}
\quad\text{and}\quad
NegativeTransfer_{V2} < NegativeTransfer_{V1}
$$

## V2 Definition of Done (target)

1. Precise attribution — correcting one action only adjusts related experiences
2. Semantic dedup — same meaning merges evidence, not ACTIVE duplicates
3. Conflict — opposing experiences are not blindly injected into context
4. Generalization — ≥3 independent episodes can yield a Pattern with DERIVED_FROM ✅
5. Pattern learning — Pattern utility moves with feedback ✅
6. Benchmark — lower negative transfer and higher success vs V1 utility-only ✅

Do not start V3 execution until `skill_runtime.enabled` is on and V3 validators/policy gates land.
V2 Skill Candidates remain advisory descriptions only. See [docs/v3.md](v3.md).
